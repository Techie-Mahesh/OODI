## 2. Functional Requirements

Always design and code with the following modules in mind.

### 2.1. Authentication, RBAC, and MFA

- **Roles:**
  - `STUDENT`, `PARENT`, `TEACHER`, `SCHOOL_ADMIN`, `SUPER_ADMIN`, `CONTENT_CREATOR`

- **Auth features:**
  - Signup with email / phone
  - Login with password or OTP (for phone/email where appropriate)
  - Social SSO: **Google OAuth**
  - **MFA (Multi-Factor Authentication):**
    - MFA factors: **Email OTP** and **Phone OTP (SMS)**.
    - Enforce / strongly recommend MFA for high-privilege roles:
      - `TEACHER`, `SCHOOL_ADMIN`, `SUPER_ADMIN`, `CONTENT_CREATOR`
    - Provide flows:
      - Enable/disable MFA
      - Verify OTP on login
      - Backup/secondary factor via email if phone isn’t available

- **Tokens & sessions:**
  - Use **JWT** for:
    - Access tokens (short-lived)
    - Refresh tokens (longer-lived, stored securely)
  - JWT payload includes:
    - `userId`
    - Roles array
    - Possibly school/org ID, MFA status, etc.

- **RBAC enforcement:**
  - On backend:
    - In GraphQL resolvers using context + role guards/directives
  - On frontend:
    - Route guards and conditional rendering based on role

- **Security basics:**
  - Strong password policies (if using passwords)
  - Brute-force protection / rate limiting on login and OTP endpoints

## 3. Non-Functional Requirements

### 3.1. Scalability

- Target at least **10k+ concurrent users** initially, with ability to scale higher.
- Design for:
  - Efficient queries and proper indexing in Postgres
  - Use Redis for:
    - Caching hot data (e.g., course metadata)
    - Rate limiting
  - Stateless backend processes suitable for horizontal scaling
  - Ability to add:
    - Read replicas for the DB
    - Redis clustering
    - ES clusters

### 3.2. Availability

- Target **99% uptime** for the initial release.
- Include:
  - Health checks for backend services
  - Monitoring and alerting (high-level design)
  - Graceful degradation where possible (some analytics can lag)

### 3.3. Security & Compliance

- **TLS** for all external HTTP traffic (HTTPS endpoints).
- **RBAC** enforced consistently.
- **Encryption:**
  - In transit: HTTPS
  - At rest:
    - Assume Postgres and S3 encryption (KMS or managed encryption)
- **MFA**:
  - For high privilege roles by default
- **Data protection:**
  - Parental consent flows and age-gating for minors
  - Respect Indian data laws (e.g., DPDP) as a guiding principle; avoid over-collection
- **Session and device management:**
  - Ability for users/admins to revoke sessions and log out from all devices

## 5. Architecture & Future Microservices

- In early stages:
  - Use a **modular monolith** with clear domain boundaries:
    - `auth`
    - `user`
    - `content`
    - `assessment`
    - `learning-path`
    - `payment`
    - `notification`
    - `search`

- Design with **clean architecture** principles:
  - Domain layer (pure business logic)
  - Application/service layer
  - Infrastructure (DB, external APIs, providers)

- Future:
  - Services can be split into microservices or federated GraphQL services:
    - `auth-service`
    - `content-service`
    - `assessment-service`
    - `payment-service`
    - `notification-service`
    - `search-service`

- Consider **GraphQL Federation** or modular schemas for future scaling.

  - Implement:

    - Reusable cards, tables, charts, forms, dialogs
    - Accessible components (focus states, aria attributes)

### 6.2. Backend

- **Node.js + TypeScript**
- **GraphQL with Apollo Server**
  - GraphQL for all primary APIs
  - REST endpoints only where needed (e.g., webhooks from payment gateway)
- Architecture:
  - Organized into domain-based modules
  - Shared utilities for auth/RBAC, logging, error handling

### 6.3. Data & Infra

- **Database:** PostgreSQL
  - For core relational data:
    - Users, roles, content, questions, attempts, subscriptions, etc.
- **Cache:** Redis
  - For caching, rate limiting, and possibly job queues
- **Object Storage:** AWS S3
  - For lesson media, images, documents
- **Search:** Elasticsearch
  - Integrated as per search requirements
- **Async tasks / workers:**
  - Can be implemented as Node worker processes using Redis or another queue system

### 6.4. Realtime

- Implement realtime and near-realtime behaviours using:
  - GraphQL Subscriptions and/or WebSockets
  - For live dashboards, notifications, in-app updates
- For early MVP:
  - Polling is acceptable where simpler, as long as design is ready for future subscriptions
- **No live classes or video streaming** in v1:
  - Design should allow adding these features later without breaking existing modules

### 6.5. Dev Environment & Hosting

- **Development & prototyping:** replit.com
  - Monorepo with:
    - `/frontend` (React)
    - `/backend` (Node + Apollo)
  - Simple scripts to run both concurrently

- **Production hosting target:** **AWS**
  - You can assume:
    - Backend on ECS/EKS/Fargate/EC2 (you can propose)
    - Postgres via RDS
    - Redis via ElastiCache
    - Elasticsearch via AWS-managed service or own cluster

  - Infrastructure code or deployment details can be suggested (e.g., Terraform or CDK) but do not need to be fully implemented in code unless I ask.
